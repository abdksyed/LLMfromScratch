Designing an India-first 40B

A plan for training a model with 40 billion parameters, the settings it learns during training. It should perform as well as Gemma 4 in reasoning, coding and tool use, while working better for Indian languages, institutions and everyday needs.

15Ttotal training tokens
28%India-focused data
200,192tokens in the vocabulary
256Ktoken context window

“India-first” means supporting India's many languages, regions and communities. It does not mean teaching one official view of India.

NASA/GSFC, India night lights 2012–2016

The decision

First, train smaller 1–3B parameter pilot models to find the best data mix. Start the expensive 40B run only after these tests. After deduplication, which means removing repeated documents, the dataset must contain at least 7.5T tokens, including at least 1T from Indian-language material. During full training, the model will read 15T tokens in total. This means useful material may be read more than once, about twice on average. Release the model only if it passes the quality and safety tests below.

01 / Pre-training

What the model will learn from

Pre-training is the first stage, where the model learns patterns from a very large dataset. Put each item in one category so it is not counted twice. For example, count an Indian programming tutorial as code, not as both code and Indian-language material.

How the numbers were chosen

Why 15T tokens and these percentages?

Why 15T total?

The Chinchilla scaling law is an older rule for balancing model size, data and compute. It suggests about 0.8T tokens for a 40B model. Newer models train for much longer: Gemma 3 27B used 14T tokens, and Llama 3 used more than 15T. We use 15T as a starting budget, then use smaller models to check whether that much training is worth the cost. [2][3][4]

Why so much code and Indian-language data?

Coding and Indian languages are main goals, so they receive a larger share than in a general-purpose model. StarCoder2 used 3.3–4.3T code tokens. Sarvam-1 reports 2T Indian-language tokens, while about one-third of Sarvam-M's later training examples used Indian languages. [8][9][11]

How the other shares were set

General knowledge gets 30% so the model keeps broad world knowledge. India-English and mixed language gets 8% for laws, public institutions and Hinglish. Science and maths gets 12% for verifiable reasoning, tools get 5% for agent skills, and other languages get 3% for transfer. The 28% India-focused total is 20% Indian-language data plus 8% India-English. These are starting assumptions, not measured optima. Compare 1–3B pilot models with different mixes before paying for the 40B run.

Can we collect enough data?

We do not already have 3T different Indian-language tokens

Sangraha contains 251B tokens across 22 languages. FineWeb2 is large, but we do not know how much useful Indian-language text will remain after copies and poor-quality material are removed. Sarvam-1 reports training on 2T Indian-language tokens, but this does not mean that 2T different tokens are publicly available and legal for us to use. [6][7][8]

≥1.0T tokens after deduplication × ≤3 readings of each document = up to 3.0T tokens read during training

Required before training: find and remove material that appears in both Sangraha and FineWeb2. Add regional books, news and broadcast transcripts that we have permission to use, along with oral-history archives and OCR (text extracted from scans). If the final collection does not reach 1T tokens, delay or reduce training. Do not fill the gap with excessive translations or repeated material.

How the 3T Indian-language training tokens are shared

Give 12 languages extra focus while including all 22 languages listed in the Constitution

The Constitution's Eighth Schedule lists 22 languages. During training, the model will read: Hindi 540B tokens; Bengali 300B; Telugu 270B; and Marathi and Tamil 255B each. It will also read Urdu 225B; Gujarati, Kannada and Malayalam 180B each; Odia and Punjabi 120B each; and Assamese 75B. The other ten listed languages receive 21B tokens each. The final 90B covers Bhojpuri, Rajasthani, Awadhi, Chhattisgarhi, Tulu, Gondi and Bhili.

This plan gives 90% of the Indian-language training tokens to the 12 focus languages. Each of the other languages in the Eighth Schedule gets at least 21B tokens during training, and 3% goes to important languages outside the list. These shares consider the number of speakers, the amount of available data and the different writing systems. They do not copy the Census population shares exactly.

02 / Preparing the data

How we prepare the training data

Keep a provenance record for every piece of training data: where it came from, whether we have permission to use it, what changes we made, and how to find and remove it if its owner asks us to. [6][7][11]

  1. 1
    Check rights and licences

    Use public-domain, openly licensed or contracted material. Keep an allow-list of acceptable code licences for each file. Reject pirated books and news.

  2. 2
    Parse each format correctly

    Use DOM parsing to keep the structure of websites, and preserve the reading order in PDFs. Keep OCR confidence scores, notebook cells, tables, LaTeX maths, lists, citations and software tests.

  3. 3
    Check language and quality

    Identify the language and script of each paragraph. Tune quality filters with native speakers. Keep real dialects, romanized text (Indian languages in Latin letters) and code-switching such as Hinglish.

  4. 4
    Deduplicate before sampling

    Use SHA-256 hashes for exact copies and MinHash to find near-duplicates. Also group translated copies and duplicated code repositories, forks and abstract syntax trees (ASTs), which represent code structure. Store each group's size.

  5. 5
    Remove private data and secrets

    Redact personally identifiable information (PII), including Aadhaar, PAN, bank, health, phone and address data. Remove passwords, API keys, private messages and doxxing, which means posting personal data to harm someone.

  6. 6
    Check filtering mistakes

    Remove illegal and directly dangerous material, but keep legitimate discussion of caste, sexuality, politics and minority dialects. Audit false positives, meaning safe text removed by mistake, for every language and community.

  7. 7
    Remove benchmark contamination

    Freeze the benchmark list first. Remove matching questions and answers using exact text, 13-token sequences, MinHash, meaning-based matches, translations and code ASTs.

  8. 8
    Verify and record the final dataset

    Run code and agent examples; check maths, names and numbers; keep AI-created data below 12%; and publish data cards and deletion logs.

03 / Tokenizer

How text will be split into tokens

The tokenizer splits text into reusable pieces. We propose a vocabulary of 200,192 pieces. This is the list of all tokens the model can recognise. Recent tests across 22 Indian languages found little improvement beyond about 200K. The token embedding matrix, which turns each token into the model's internal representation, also uses parameters. At this model width, a 200K vocabulary uses about 1.64B parameters, while Gemma 4's 262K vocabulary would use about 2.15B. The smaller vocabulary leaves more parameters for language and reasoning. [1][13]

Train one shared byte-pair encoding (BPE) tokenizer, which learns common text pieces from the full data mix. Use about 180K pieces inside word boundaries, then about 19K sentence-bounded “superwords” for common prose phrases. UTF-8 byte fallback ensures that any unseen text can still be read. Keep each code or JSON field separate. For example, do not create one token that combines the end of one field with the beginning of the next.

Token fertility: how many pieces should one word become?

Measure on native text from sources not used to train the tokenizer. Each number is the average tokens needed for one Unicode word; lower is better.

The average must be no more than 1.95 tokens per word. No language may exceed 3.0, and UTF-8 byte fallback on clean text must stay below 0.1%. Report every language's median (P50), difficult tail (P95), bytes per token and sequence length. Do not let a good Hindi score hide a poor Santali score.

Use NFC, a conservative Unicode normalization: computers can store the same visible character in different ways. Preserve nukta, ZWJ/ZWNJ joining controls, Vedic marks, Urdu diacritics, emoji and original whitespace. Carefully reviewed compatibility fixes may be used for prose, but never as general replacements in code, maths or JSON. Tokenizing and decoding must reproduce every byte of the original input.

Why these tokenizer numbers?

Vocabulary size, context length and fertility trade off against cost

Why 200,192 vocabulary entries?

IndicSuperTokenizer experiments found little benefit beyond about 200K entries across the 22 Indian languages. The exact total is an accounting choice: 198,912 learned pieces + 256 byte-fallback pieces + 1,024 control markers = 200,192. This also saves about 0.5B parameters compared with Gemma 4's 262K vocabulary. [1][13]

Why a 256K context window?

The Gemma 4 report publishes long-context results at 128K and about 256K, making 256K a defensible comparison point. It can hold long legal documents, code repositories and tool traces in one request. Moving to 1M would greatly increase memory, latency and serving cost without a matching Gemma 4 result in the report. [1]

Why these fertility ceilings?

These are provisional acceptance targets, not published measurements. English at 1.15 is the efficiency anchor. The higher ceilings for languages such as Malayalam, Manipuri, Sanskrit and Santali allow for harder morphology, scripts or less training data. We will replace these assumptions with held-out native-text measurements. The current 22 ceilings average 1.92, leaving a small margin below the 1.95 gate, and no language is allowed to exceed 3.0.

04 / Post-training and alignment

Teach the model to answer, use tools and act safely

Use executable rewards: scores from unit tests for code, symbolic checks for maths and safe simulations for tool use. For subjective answers, use trained reviewers. A learned reward model is an AI grader trained on those reviews. It may provide at most 20% of the score. It can never overrule a failed test, tool policy or unauthorised side effect. [14]

Why 3.2M SFT and 1.2M DPO?

The SFT total is the sum of the task quotas below: 650K India and Indian-language + 650K code + 600K tools + 500K maths and science + 450K sourced answers + 200K long context + 150K safety = 3.2M. Fourteen billion tokens means about 4,400 tokens per conversation. DPO is set to 1.2M, or one preference pair for every 2.7 SFT examples. Three reviewers check 300K pairs, which is 25% of the DPO set.

Why 420K × 16 and 120K × 8?

RLVR uses 120K maths, 120K code, and 60K each for science, SQL and tool tasks, totalling 420K. Sixteen attempts per task produce 6.72M scored attempts and give the model several ways to find a correct answer. Agent episodes are longer and more expensive, so we use 30K tasks in each of four Indian domains and eight attempts, totalling 960K episodes. Pilot runs should compare 8 versus 16 attempts.

Why 550K safety examples?

Start with 25K adversarial, refusal and correction examples for each of the 22 languages in the Eighth Schedule. That gives 550K and prevents the largest languages from dominating safety training. The risk types must cover privacy, fraud, violence, self-harm, sexual safety, hate, caste abuse, misinformation and unauthorised tool use. These counts are proposed budgets, not numbers reported by Tülu 3. [14]

What the SFT examples cover

Use 650,000 India and Indian-language tasks, 650,000 coding tasks and 600,000 browser, terminal and office-tool trajectories (recorded action sequences). Add 500,000 maths and science tasks, 450,000 grounded answers supported by sources, 200,000 long-context and RAG tasks, and 150,000 safety examples. RAG means answering with retrieved documents.

Of the natural-language examples, 45% use the 12 focus languages, 10% use the other languages listed in the Constitution, 10% mix languages naturally, such as Hinglish, and 35% use English. At least 25% of coding and tool requests are in an Indian language or Hinglish.

How practice attempts are scored

Give 55% of the score for the correct result and 15% for following the instructions and required tool format. Give 10% each for supporting evidence, working efficiently and using clear language. Any serious unsafe action or use of a tool without permission ends the attempt with a failure score of −1. Score the final result, not a persuasive-looking chain of thought.

Before using an AI grader, compare it with native-speaking reviewers in every language. Its ROC-AUC must be at least 0.80, meaning it ranks better answers above worse ones reliably. Calibration error is the gap between stated confidence and actual accuracy. It must be at most 0.05. Human agreement measured by weighted kappa (κ) must be at least 0.65. People independently recheck 5% of attempts to catch reward hacking. This is when the model exploits the scoring rules without doing the task well.

Represent many Indian perspectives

Follow the constitutional values of dignity, equality, liberty, freedom for different religions, privacy and child safety. For disputed history, religion, caste, borders or politics, say which time and place the answer covers. Separate facts, laws and opinions, and be clear when the evidence is uncertain. Reviewers must include Dalit, Adivasi, religious-minority, LGBTQ+, disabled, rural, urban and regionally diverse people. Do not force all reviewers to agree when reasonable disagreement exists within India.

05 / Evaluation and launch tests

How we decide if the model is good enough

Before training, freeze the training-data cutoff date and benchmark list. Test this model and Gemma 4 31B with the same evaluation harness, which is the program that runs and scores the tests. Use the same prompts, tools and settings. Run three random seeds, meaning three repeatable runs with different random starting choices. Report a 95% confidence interval. This is the range in which the true score is likely to fall. Also show the weakest language, not only the overall average.

Comparing with Gemma 4

Use a two-point non-inferiority margin as the largest allowed gap

“As good as Gemma 4” needs a rule chosen before seeing the results. A non-inferiority margin is the largest gap we will accept. For every benchmark scored as a percentage, subtract Gemma 4's score from this model's score. Then use paired bootstrap: repeatedly draw samples from the same test questions to estimate a 95% confidence interval for the difference. Even the lower end of that interval must remain inside the allowed gap. This stops us from treating small, noisy changes as certain. [17][18]

A two-point margin allows at most two extra failures for every 100 tasks. This is our maximum allowance. Gemma 4 did not publish a two-point allowance. Each benchmark may set a smaller margin. If a test has too few questions to measure a two-point gap reliably, add questions instead of accepting a larger gap. For safety and tool use without permission, the allowed gap is zero.
