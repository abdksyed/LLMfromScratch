Cleaning an agentic SWE corpus

Nine strategies from the session applied to denovoswe_traj_filtered.jsonl — 11,463 agent trajectories of DeepSeek-v4-pro solving GitHub pull requests from scratch, totalling 4.62 GB.

The short answer

All nine strategies taught in the session were applied. Six transform or tag content in place (boilerplate, normalisation, ghost tags, language ID, PII scrubbing, manifest). Three drop whole records (quality filtering, de-duplication, decontamination). The dominant cut — 73 % of records — came from keeping only trajectories where the agent passed every unit test in the target repository.

00 / Dataset

What we started with

DeNovoSWE is a corpus of agentic software-engineering trajectories. Each record is one complete conversation: a GitHub PR specification sent to DeepSeek-v4-pro, followed by every tool call and response the model produced while implementing the repository from scratch. A test harness then ran the repo's own test suite and recorded the pass rate as extra_info.score.

What is extra_info.score?

Every trajectory carries a test-suite pass rate baked in at dataset creation time. After the agent finished writing code, the DeNovoSWE harness:

1. Installed the agent's implementation into the target environment.
2. Ran the repository's own unit tests — the same tests the PR author would have used.
3. Recorded score = tests_passed / tests_total (0.0 – 1.0).

Score distribution: 0.6 → 142 · 0.7 → 637 · 0.8 → 1,783 · 0.9 → 3,746 · 1.0 → 5,154. Only the 5,154 perfect-score records were candidates for the SFT corpus. After rollout collapse (keeping one per issue) 1,212 survived.

Why so much removed?

The 73 % verifier cut is intentional SFT curation, not aggressive cleaning. For supervised fine-tuning you only train on demonstrations of correct behaviour. A trajectory where 3 out of 35 tests fail teaches the model to make the same mistakes. The 15 % rollout-collapse cut is also structural: the dataset runs each GitHub issue 4–5 times to increase diversity; for SFT we need one canonical successful run per task.

Together these account for 88.6 % removal. The remaining 0.9 % is real quality noise: stack traces repeated 50+ times, diff-heavy tool outputs with a symbol ratio above the prose threshold, and 6 near-identical trajectories that solved the same trivial repo.

If you want partial-credit data (e.g. for RL), lower the score gate to 0.8 — that retains 8,137 records before rollout collapse.

  • What the session says

    Raw scraped data carries nav menus, cookie banners, and HTML chrome. Drop them immediately — this step alone removes ~8 % of typical web crawl data.

    What this dataset has instead

    Agent corpora don't have cookie banners. The equivalent boilerplate is: (1) an identical 8,700-character system prompt on every one of the 11,463 records — 1 unique prompt, copied 11,463 times; (2) an identical JSON tool schema on every record; (3) pip installer walls inside tool-observation messages, and (4) ANSI colour escape sequences and carriage-return progress bars from terminal output.

    The system prompt and tool schema were hoisted to reference IDs (system_ref, tools_ref) so they are stored once. This removed 18 M characters of pure repetition. Per-message: 15,450 pip-noise lines, 1,278 separator bar lines, 154 CR-progress messages, and 142 messages containing ANSI escape sequences were stripped.

  • What the session says

    Remove invisible tokens (zero-width spaces, HTML unescapes, non-breaking spaces) but be context and language-aware. Never touch tabs or leading spaces in Python code. Never strip ZWJ/ZWNJ from Brahmic scripts.

    Applied here

    Code is fenced before any rule runs — fenced/inline code blocks are replaced with placeholders, rules apply to prose only, then code is restored. Zero-width spaces (U+200B), BOM (U+FEFF), soft-hyphens, and word joiners are removed universally. ZWJ/ZWNJ are stripped only when no Brahmic-script characters are present (none were found — this corpus is entirely ASCII+Latin). HTML entities are double-unescaped since some content had &amp;lt; double-encoding. Trailing whitespace per line is stripped; leading indentation is never touched.

    17,019 messages were modified — about 13 % of all messages. The character count dropped by 2.3 M chars (221.3 M → 218.9 M), almost entirely from the boilerplate hoisting in strategy 1 carrying over.

  • What the session says

    Different datasets use varied role markers (<|user|>, System:, triple hashes). If left in pre-training data the model wastes compute learning multiple meaningless names for the same role.

    Applied here

    The dataset is structurally clean — roles live in the role JSON field, not embedded in content. However, 15 messages had leaked tokens from other model families: <|im_start|>, <|im_end|>, [INST], [/INST], <s>, </s>. These were stripped from prose. When the same tags appeared inside a code fence (e.g. a tutorial showing tokenizer output), they were escaped instead of deleted — preserving the educational content.

    Low frequency here (0.02 % of messages) but the cost of leaving them in is high: the model learns to associate Llama or Qwen role syntax with the tool-use format, causing cross-contamination between model families.

  # Tutorial content preserved

    Ghost tags removed from prose; escaped inside code fences so tutorials survive.

  • What the session says

    Never trust folder names. Evaluate language at runtime; throw away documents that don't match target languages. This catches Bengali mislabelled as Assamese, English slipping into Hindi corpora, etc.

    Applied here

    Code confuses every language detector, so prose extraction runs first: fenced code, diffs, tracebacks, and file paths are stripped, leaving only natural-language prose. langdetect (seeded for reproducibility) is run on the first 20,000 characters of prose. If <200 chars of prose remain the record is tagged code-dominant and kept (dropping it would delete valid purely-code trajectories).

    This corpus turned out to be 100 % English — no surprises. The check still matters: a later collection run could mix in Chinese DeepSeek rollouts without the metadata changing, and this gate would catch them automatically.

  • What the session says

    Two layers: (A) deterministic heuristics — mean word length 3–10, symbol-to-word ratio, duplicate-line ratio; (B) LLM classifier trained to score educational value.

    Layer A — heuristics (87 records dropped)

    Applied on extracted prose (not raw content). Dup-line ratio > 0.30 caught 55 records: trajectories where the tool observations were dominated by the same stack-trace line repeated 50–200 times (a crash loop the agent couldn't recover from). Symbol ratio > 0.10 caught 35 records: diff-heavy tool output with almost no prose words, just +/- prefixes.

    Layer B — verifier score (8,386 records dropped)

    The dataset provides something stronger than a trained proxy scorer: the repo's own test-suite pass rate. extra_info.score == 1.0 means every test in the target repository passes. This is a ground-truth correctness signal, not a learned approximation. Gate set at 1.0 (strict) for SFT. Lower it to 0.8 for RL or curriculum learning.

    Example: social-app-django_pr812 score = 0.971 → 34/35 tests passing → dropped. The one failing test indicates the agent made a systematic error — we don't want to teach that pattern.

  • What the session says

    Three tiers: exact duplicates, near-duplicates (Jaccard ≥ 0.67 via MinHash + LSH on 8-word shingles), and rollout duplicates in RL datasets. Done centrally on the full dataset.

    6a — exact ID (0 removed)

    No records shared the same id string. The id encodes batch folder + instance id, so different runs produce different ids automatically.

    6b — rollout collapse (1,771 removed)

    2,768 unique GitHub issues, but 11,463 records = each issue averaged 4.1 attempts. Groups sorted by (score desc, steps asc, nbytes asc) — best score wins; among ties, shortest trajectory wins. Example: necaris_cuid.py_pr1 appeared 5 times, all scoring 1.0 — 4 redundant copies removed.

    6c — MinHash near-dupe (6 removed)

    128-permutation MinHash over 8-word shingles; LSH threshold 0.67. Found 6 trajectories solving essentially the same trivial utility repository (a cuid generator, a base58 encoder) where different batch runs produced nearly identical code and explanations.

    Training on the same trajectory multiple times causes harmful memorisation — the model over-fits to a single solution pattern rather than generalising.

  • What the session says

    Applied here

  • What the session says

    Run n-gram / shingle overlap checks against benchmark datasets. Throw away shards that contain leaked test data to ensure benchmark scores are legitimate.

    Applied here

    Two levels of checking: repository-level (cheap, structural) and n-gram probe (expensive, content-level).

    Repo level: The 32 known SWE-bench evaluation repositories (django, sympy, scikit-learn, matplotlib, requests, flask, pytest, pylint, sphinx, astropy, xarray, seaborn, and others) are hard-listed. Any trajectory whose instance_id resolves to one of those repos is dropped immediately, without parsing content. Found 1 record: a trajectory for the requests library.

    N-gram probe: 8-gram overlap is checked against known benchmark prompt strings (HumanEval, MBPP, GSM8K style problems). No matches found — this corpus is entirely repository-implementation tasks, not Q&A benchmarks.

    Training on a task from the SWE-bench evaluation set inflates the reported solve rate. Even one leaked task can shift the score by 0.1–0.3 % on a 300-task benchmark — enough to misrepresent the model's ability.

  • What the session says

    Generate a manifest for every finalised shard documenting source, license, token count, language distribution, and the cryptographic hash of the cleaning scripts used. This makes the shard reproducible.

    Applied here

    One manifest-NNNN.json is written alongside each shard-NNNN.jsonl.gz. It records: shard name, creation UTC, source dataset, license, record count, token count (cl100k_base), language distribution, source model distribution, minimum verifier score, a sample of instance IDs, the SHA-256 of the shard's JSONL content, the SHA-256 of the compressed file, and — critically — the SHA-256 of the cleaning script itself.

    If the cleaning script changes (a bug fix, a threshold change), the script hash changes, making the old shards distinguishable from new ones even if the file names stay the same. The full pipeline report (report.json) records every counter, config parameter, and library version used.

    Without manifests, "I cleaned the data" is not reproducible. With them, anyone can verify exactly which version of the pipeline produced a given shard — and re-run it to get the same bytes.

Beyond the class list

Concerns specific to agent corpora

Three cleaning concerns don't appear in the standard nine strategies because they only arise in RL rollout and agentic trajectory datasets. Each was addressed before the nine-strategy pipeline ran.

RL rollout structure

This corpus was built by running each GitHub issue 4–5 times to increase the chance of finding a successful solution. For web crawls this pattern doesn't exist; for agent corpora it's the dominant duplicate class. Standard MinHash can't detect these because the prose differs substantially (different code, different reasoning). A dedicated instance-ID grouping pass (strategy 6b) was needed before MinHash ran, collapsing 11,463 → 1,305 survivors.

Terminal chrome contamination

Tool observations in agent trajectories contain output that would never appear in web text: ANSI colour escape codes (\x1b[32mPASSED\x1b[0m), carriage-return progress bars (100%|████████|), and pip installer walls. These are invisible in a terminal but become noisy tokens in a corpus. 142 ANSI messages, 154 CR-progress messages, and 15,450 pip-noise lines were stripped as part of strategy 1 before any other cleaning.

Hoisted repeated metadata

Every record carried an identical 8,716-character system prompt and an identical JSON tool schema — totalling ~18 M characters of pure repetition across 11,463 records. Web crawls don't have this; agent corpora always do. The pipeline hoists both to content-addressed IDs (system_ref, tools_ref), stores them once, and references them by SHA-256 prefix in each output record — recovering the full content at training time from a lookup table.

Verifier score as quality classifier

The session describes training a small proxy LLM to rate educational value. This dataset ships with something stronger: an executed test-suite verdict. extra_info.score = tests_passed / tests_total is ground truth, not a learned approximation. The proxy LLM approach would be needed if the dataset lacked this field — for example, when cleaning general web text. Here we used the existing signal directly.

Copyright-safe PII scrubbing

Open-source repositories legally require attribution lines (# Copyright (c) 2023 Jane Doe). Standard PII scrubbers would strip these because they contain real names. The pipeline identifies and protects 1,905 copyright lines before running the email/name scrubber, then restores them after — satisfying both the privacy requirement (no contactable identifiers) and the license requirement (attribution preserved).

Functional-code IP preservation

The IP scrubber uses a classifier rather than a blanket regex. Private ranges (127.x, 10.x, 192.168.x, 172.16–31.x), link-local (169.254.x), and multicast (224+) are kept because they appear in working code. Public IPs are redacted. Version strings that happen to match four-octet format (e.g. 1.2.3.400) are detected by the 0–255 range check and kept. Result: 655 public IPs redacted, 1,289 local IPs preserved.

One contaminated repository found: the requests library (psf/requests) is one of the 12 original SWE-bench evaluation repos. One trajectory targeting it was dropped at the decontamination gate. No other SWE-bench repos appeared in the filtered corpus — but the gate is structural and would catch any new additions automatically if the corpus is extended.
